# Area Guides 自動化計画（BMAD METHOD準拠）

このドキュメントは、area-guidesプロジェクトで将来BMADエージェントで自動化したいことを整理した「ネタ帳」です。  
実装の詳細ではなく、「やりたいことリスト＋ざっくり手順」レベルで記載しています。

## 1. 賃料データの四半期更新フロー

### ゴール
SUUMO / HOME'S などの不動産サイトから最新の賃料データを取得し、`content/area/{slug}.yml` の `rent_by_type` フィールドを自動更新する。

### 手順（想定）
1. SUUMO / HOME'S のAPIまたはスクレイピング（倫理的・法的に問題ない範囲で）から賃料データを取得
2. 四半期ごとの平均値を計算（1K, 1LDK, 2LDK, 3LDK）
3. `content/area/{slug}.yml` の `rent_by_type.quarter` を更新（例: `2025-Q1` → `2025-Q2`）
4. `rent_by_type.{room_type}` の `min`, `max`, `typical` を更新
5. 変更をコミット前に、`docs/area-guides-bmad-brief.md` の「定期的に更新したい変数」セクションを確認
6. `/areas` と `/areas/{slug}` ページで自動反映されることを確認

### 注意点
- データソースの信頼性を確保（SUUMO / HOME'S の公式データを優先）
- 参考ブログの数値は「推定値」として扱い、可能な限り公式データソースで検証
- 検証できない数値は `null` または `TODO` コメントとして残す

---

## 2. 新しい区を追加するときの自動テンプレ生成

### ゴール
新しい区（例: `minato`, `chiyoda`）のエリアガイドLPを、最小限の手動入力で生成する。

### 手順（想定）
1. BMADエージェントに「新規エリア追加」プロンプトを実行
2. `content/area/{slug}.yml` の雛形を生成：
   - `bmad/prompts/area-variables.schema.json` に基づいた基本構造
   - `slug`, `title`, `locale`, `status: "Draft"` を初期値として設定
   - その他のフィールドは `null` または空配列で初期化
3. 画像のプレースホルダを生成：
   - `public/images/{slug}/` ディレクトリを作成
   - `assets.hero.path`, `assets.map.path` を設定（画像ファイルは後で配置）
   - `assets.gallery` は空配列で初期化
4. `/areas/{slug}` LP の初期バージョンを生成：
   - `DefaultAreaLanding` コンポーネントを使用
   - 必要に応じて、`ShibuyaStoryLanding` のような専用レイアウトを選択可能にする
5. `/areas` 一覧ページに自動追加（`content/area/{slug}.yml` が存在すれば自動表示）

### 注意点
- 新規エリアは `status: "Draft"` で開始し、完成したら `status: "Published"` に変更
- 画像ファイルは後で手動で配置する前提（AIが画像を生成・配置するのは別タスク）
- `data/wards/` には原則として追加しない（`content/area/*.yml` を SoT に）

---

## 3. 画像の差し替え・追加のワークフロー

### ゴール
画像を `public/images/{slug}/` に配置し、YAMLの `assets` ブロックを自動更新する。

### 手順（想定）
1. 画像ファイルを `public/images/{slug}/` に配置（命名規則に従う）
   - `{slug}-hero.{ext}`
   - `{slug}-map.{ext}`
   - `{slug}-gallery-01.{ext}`, `{slug}-gallery-02.{ext}` など
2. `content/area/{slug}.yml` の `assets` ブロックを更新：
   - `assets.hero.path` を設定
   - `assets.hero.alt` を英語・日本語両方で記入
   - `assets.map`, `assets.gallery` も同様に更新
3. Lintでの検証：
   - `bmad/prompts/area-variables.schema.json` に基づいてバリデーション
   - 画像ファイルの存在確認（`public/images/{slug}/` に実際にファイルがあるか）
   - `alt` テキストの存在確認（アクセシビリティ）
4. 変更をコミット前に、`/areas/{slug}` ページで画像が正しく表示されることを確認

### 注意点
- **画像ファイルを `public/images/` に直置きするだけは禁止**
- 必ず YAML にパスとaltを登録してから使うこと
- AIが新しい画像を追加する際も、このルールに従う

## 4. 年間イベント情報の更新

### ゴール
区の公式サイトや観光協会の情報から、年間イベント情報を取得し、`content/area/{slug}.yml` の `events` フィールドを更新する。

### 手順（想定）
1. 区の公式サイトや観光協会の情報を取得：
   - 公式サイトのイベントカレンダーをスクレイピング（倫理的・法的に問題ない範囲で）
   - または、公式サイトからJSON/CSV形式でエクスポート
2. イベント情報を正規化：
   - `name`（英語・日本語）
   - `month`（開催月）
   - `description`（英語・日本語）
3. `content/area/{slug}.yml` の `events` フィールドを更新
4. 年によって変動する可能性があるイベントは、その旨をコメントで明記
5. 変更をコミット前に、`/areas/{slug}` ページでイベント情報が正しく表示されることを確認

### 注意点
- イベント情報は、区の公式サイトや観光協会の情報を優先する
- 年によって変動する可能性があるイベントは、その旨をコメントで明記
- 月（`month` フィールド）は、実際の開催月を確認してから記載する

## 5. アクセス時間の自動更新

### ゴール
JR東日本や東京メトロの公式サイトから、主要駅への所要時間を取得し、`content/area/{slug}.yml` の `commute_times` フィールドを更新する。

### 手順（想定）
1. JR東日本や東京メトロの公式サイトから所要時間を取得：
   - 公式サイトの路線検索APIを使用（利用可能な場合）
   - または、公式サイトの時刻表から所要時間を抽出
2. 各停と急行の両方を取得（可能な場合）
3. `content/area/{slug}.yml` の `commute_times` フィールドを更新：
   - `destination`（目的地）
   - `minutes`（所要時間）
   - `type`（`express` または `local`）
   - `line`（路線名）
4. 変更をコミット前に、`/areas/{slug}` ページでアクセス情報が正しく表示されることを確認

### 注意点
- 主要駅への所要時間は、JR東日本や東京メトロの公式サイトで確認する
- 各停と急行の両方を記載する場合は、実際の時刻表を参照する
- 路線名（`line` フィールド）も正確に記載する

---

## 6. サブエリア情報の自動生成

### ゴール
参考ブログ記事や区の公式情報から、サブエリア情報を抽出し、`content/area/{slug}.yml` の `subareas` フィールドを更新する。

### 手順（想定）
1. 参考ブログ記事や区の公式情報からサブエリア情報を抽出：
   - 人気エリアランキング
   - 各エリアの特徴・説明
   - ハイライト（ショッピング、飲食、公園など）
2. サブエリアの選定：
   - その区で実際に人気があるエリアを選ぶ
   - 参考ブログに載っていても、実際の居住エリアとして一般的でない場合は除外
3. `content/area/{slug}.yml` の `subareas` フィールドを更新：
   - `name`（英語・日本語）
   - `description`（英語・日本語）
   - `highlights`（配列）
4. 変更をコミット前に、`/areas/{slug}` ページでサブエリア情報が正しく表示されることを確認

### 注意点
- サブエリア（`subareas`）は、その区で実際に人気があるエリアを選ぶ
- 参考ブログに載っていても、実際の居住エリアとして一般的でない場合は除外する
- 各サブエリアの説明は、そのエリアの特徴を簡潔に伝える
- **参考ブログの文章はそのままコピペしない**。内容だけを参考にして、独自の文章に書き換える

---

## 7. FAQの自動生成・更新

### ゴール
よくある質問を自動生成し、`content/area/{slug}.yml` の `faq` フィールドを更新する。

### 手順（想定）
1. よくある質問のテンプレートを定義：
   - 賃料関連の質問
   - アクセス関連の質問
   - 治安関連の質問
   - 外国人向けサービスの質問
   - 生活アメニティ関連の質問
2. 各エリアの特性に合わせて質問をカスタマイズ：
   - エリアの特徴に応じた質問を追加
   - 回答をエリアのデータに基づいて生成
3. `content/area/{slug}.yml` の `faq` フィールドを更新：
   - `q`（質問：英語・日本語）
   - `a`（回答：英語・日本語）
4. 変更をコミット前に、`/areas/{slug}` ページでFAQが正しく表示されることを確認

### 注意点
- FAQの質問と回答は、エリアの特性に合わせてカスタマイズする
- 回答は、エリアのデータ（賃料、アクセス、生活アメニティなど）に基づいて生成する
- 参考ブログの文章はそのままコピペしない。内容だけを参考にして、独自の文章に書き換える

---

## 8. 多言語対応の拡張

### ゴール
将来的に、韓国語、中国語、ベトナム語などの言語を追加する。

### 手順（想定）
1. `bmad/prompts/area-variables.schema.json` の `locale` フィールドを拡張：
   - `["en", "ja"]` → `["en", "ja", "ko", "zh", "vi"]` など
2. `content/area/{slug}.yml` の各フィールドに多言語対応を追加：
   - `title.ko`, `title.zh`, `title.vi` など
   - `overview.ko`, `overview.zh`, `overview.vi` など
3. `docs/area-guides-bmad-brief.md` の「今後の拡張メモ」セクションを更新
4. UIコンポーネントで多言語対応を実装（別タスク）

### 注意点
- まずは日本語と英語だけ対応する
- 将来は韓国語、中国語、ベトナム語などを追加するが、そのときも基本ルールは `docs/area-guides-bmad-brief.md` に追記する
- BMAD のエージェントは必ず `docs/area-guides-bmad-brief.md` を最初に読む前提でプロンプトを設計する

## 9. データの真実の源（SoT）の統一

### ゴール
将来的に、`data/wards/*.ts` を廃止し、`content/area/*.yml` に一本化する。

### 手順（想定）
1. `data/wards/setagaya.ts` のデータを `content/area/setagaya.yml` に移行：
   - 詳細データをYAML形式に変換
   - 既存の `content/area/setagaya.yml` とマージ
2. `data/wards/` ディレクトリを段階的に廃止：
   - 新規エリアは `content/area/*.yml` のみを使用
   - 既存の `data/wards/*.ts` は、移行が完了するまで残す
3. `lib/area-loader.ts` を更新：
   - `loadWardRich` 関数を廃止
   - `loadAreaYaml` のみを使用するように変更
4. `docs/area-guides-bmad-brief.md` の「データの真実の源（Source of Truth）」セクションを更新

### 注意点
- **SoTのルールを変えるときは、まず `docs/area-guides-bmad-brief.md` を更新してから、実装に手をつけること**
- コードを先に変更してからルールを後付けするのは禁止
- 段階的に移行し、既存の動作を壊さないようにする

## 10. コンポーネントの統一

### ゴール
`components/ward/` を段階的に廃止し、`components/areas/` に統一する。

### 手順（想定）
1. `components/ward/` の機能を `components/areas/` に移行：
   - `components/ward/*-section.tsx` を `components/areas/` に移動
   - 必要に応じて、コンポーネント名を変更
2. `app/[ward]/page.tsx` を更新：
   - `components/ward/ward-guide-layout.tsx` の代わりに、`components/areas/` のコンポーネントを使用
3. `components/ward/` ディレクトリを段階的に廃止：
   - 移行が完了したら削除
4. `docs/area-guides-bmad-brief.md` に移行完了を記録

### 注意点
- 段階的に移行し、既存の動作を壊さないようにする
- `/setagaya` や `/areas` の動作が壊れていないか確認する
